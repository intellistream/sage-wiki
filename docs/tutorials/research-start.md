# 新成员入门：从读论文到完成一次系统实验

本路线适合刚接触推理系统、检索或状态管理的同学。目标是形成一个可解释、可复现的小实验，而不是先把所有论文读完。

## 先选一个明确的问题

从下面三个入口选一个。每次只选择一个主要指标，并写清正确性约束。

| 入口 | 可以观察的问题 | 首次实验产物 |
| --- | --- | --- |
| 推理执行与服务 | 长输入为什么拖慢短请求？并发提高后尾延迟如何变化？ | 请求长度、到达率与延迟分布的对应表 |
| 状态管理 | KV cache 在什么时候分配、复用、迁移或释放？ | 一张状态生命周期图和一组内存观测 |
| 检索与记忆 | 知识更新后，回答是否仍引用旧版本？ | 一组带标准来源的问答，以及更新前后检索结果 |

例如，把“优化 RAG”收窄为：“同一批文档中替换一条已失效知识后，检索结果何时不再返回旧条目？”这能明确输入、更新动作、预期输出和失败条件。

## 第一步：建立最小概念框架

先读[LLM 推理入门](llm-inference-basics.md)，区分 prefill、decode、批处理与 KV cache。再读[系统研究概览](../achievements/sage-system-overview.md)，定位你研究的是执行、信息维护还是在线调控。

准备一页笔记，回答：

- 系统接收什么输入，产出什么结果？
- 关键状态存在哪里，由谁创建和释放？
- 请求经过哪些阶段，哪一步可能等待？
- 正确性如何判断，性能指标是什么？

不能回答时，先画出数据流与状态流，再读更多优化机制。

## 第二步：带着问题读论文

按[论文阅读路径](../resources/inference-systems-reading-path.md)选择一篇直接相关的论文。第一次阅读只交付一页问题卡：

```text
论文与版本：
目标负载：
现有方法在哪个条件下失效：
机制改变了什么数据结构、调度决策或访问路径：
正确性依赖哪些假设：
作者如何建立基线：
我最想复核的一个结论：
```

第二次阅读追踪一条完整请求，标出机制在哪一步生效。第三次阅读实验设置，核对模型、硬件、数据集、缓存状态、并发和到达过程。不能把论文摘要中的加速比直接当作自己环境的预期收益。

## 第三步：跑通未修改基线

在获分配的设备上记录代码提交、依赖版本、模型修订和启动参数。先做一个最小正确性请求，再做短小、固定的负载。按照[服务部署与验收](serving-acceptance.md)检查实际模型、工具执行和返回结束状态。

基线应保留原始结果与失败请求。只记录平均吞吐会漏掉超时、排队和长尾；至少同时报告成功率、吞吐、首 token 延迟和端到端延迟。具体指标见[Benchmark 指南](../resources/inference-benchmark-guide.md)。

## 第四步：只改变一个因素

选择一个配置或机制开关，在相同输入与资源上做对照。先验证答案或状态语义没有改变，再比较性能。分别报告冷启动、预热后和缓存命中的结果。

若没有收益，先检查机制是否实际启用、负载是否触发它、测量是否覆盖它影响的阶段。不要立即增添第二个优化。负结果也有价值：它说明适用条件或成本边界。

## 怎样算完成第一次实验

- 别人能根据记录重现同一负载。
- 能指出优化发生在哪个阶段，并提供可观测证据。
- 能解释一个失败样例或没有收益的条件。
- 结论区分“功能可用”“结果正确”“性能改善”。

继续选题前，按[研究问题框架](../standards/research-problem-framework.md)检查问题是否具有普遍性，再用[论文修改清单](../standards/paper-revision-checklist.md)整理论证。
