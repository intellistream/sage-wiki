# Wiki、知识库与分身：内容更新的完整流程

Wiki 是供人阅读、协作修改的公开文档。检索知识库是供应用寻找证据的运行时数据。分身根据问题选择材料并组织答案。三者相互连接，但更新其中一处并不自动证明其他两处已生效。

## 内容从哪里来

```text
经审核的公开来源 → Wiki / 公开主页 → 文档解析与稳定来源标识
                                      ↓
                               检索索引与持久化
                                      ↓
                         召回 → 重排 → 回答及可访问引用
```

每份材料至少应有标题、来源标识、可访问的来源地址、适用范围和核查日期。可见范围需要单独审查，不能仅凭文件名或一个 public 标签决定公开内部材料。

## 修改、删除和替换的规则

| 情况 | 文档处理 | 知识库处理 |
| --- | --- | --- |
| 同一来源内容修订 | 原位置更新，说明重要变化 | 按稳定来源标识更新，避免制造重复文档 |
| 页面改名或合并 | 更新导航和内部链接 | 删除不再存在的旧来源，再加入新来源 |
| 时间敏感事实失效 | 核实当前来源后修改或撤下 | 旧片段与索引一起失效，不能只删网页 |
| 历史论文或实验 | 保留日期、版本和实验条件 | 作为历史证据，不替代当前部署信息 |
| 来源无法核实 | 标记待核查并停止当作现行事实使用 | 保留可恢复备份，退出当前事实检索 |

不应仅凭文档很旧就删除它。论文、设计记录和历史实验可能仍有价值；重点是避免把特定时间、配置下的结果当成今天的通用结论。

## 索引更新需要检查什么

**来源身份稳定**：网页去掉标题、修改版式，不应让同一人物或项目突然变成另一份来源。身份由稳定标识承载，标题只负责展示。

**删除传播完整**：从源文件消失的文档，应从记录、向量索引和关联检索中退出。还要检查旧导入脚本是否会重新写回它。

**向量空间一致**：embedding 模型、维度或预处理改变后，需要按兼容性规则重建索引。不能把不同生成方式的向量混在同一个索引里比较相似度。

**引用能离开 Wiki 使用**：文档内部的相对 Markdown 链接，进入分身的检索材料时应转成完整公开 URL，否则回答中会出现相对于聊天页面的断链。

**权限保持一致**：索引更新、重排、缓存与引用展示都应遵循同一可见范围。公开文档迁移不应顺带公开内部名单、会议记录或未发表材料。

## 大批量修订的安全切换

先记录当前文档清单与校验值，在副本里刷新来源、删除已确认的失效条目并构建索引。核对文档数、索引完整性、关键身份与典型问题后，再切换服务读取的目录。切换前应重新检查原库是否出现新写入，原库保留为回滚备份。

## 用问题验收，而不只看条目数

准备三类小样本：一条新知识、一条被修改的事实、一条应被撤下的旧知识。分别核对召回来源、重排结果、最终答案和链接。

- 新知识能被问到，答案能指出证据。
- 修改后的问题采用新结论，不再引用旧段落。
- 已撤下条目不再被召回，证据不足时明确说明。
- 同步再次运行没有变化时，不重复重建索引或重启服务。

分身回答不符合预期时，还要检查意图路由是否跳过检索。文档正确但问题被错误地送到“运行时状态查询”，同样无法得到正确知识回答。
