# Wiki 内容贡献与维护规范

Wiki 的目标是让读者能够理解一个问题、完成一个操作或复核一个结论。单纯收集链接或复述项目宣传，通常不足以形成一篇可用文档。

## 一篇文章至少回答什么

1. **适用对象与前提**：面向谁，需要哪些知识、环境或权限？
2. **具体问题**：读者遇到了什么症状，本文解决到哪一步？
3. **方法与原因**：关键步骤是什么，为什么这样做？
4. **验证方法**：看到什么输出才算成功，失败时从哪里定位？
5. **来源与边界**：事实依据在哪里，哪些结论仅适用于特定版本或负载？

入门文章优先解释概念和最小例子；操作指南提供前提、步骤、验收与恢复；研究笔记应区分已复现结果、作者主张与自己的假设。

## 可直接采用的结构

```markdown
---
title: 描述具体问题的标题
date: YYYY-MM-DD
---

# 描述具体问题的标题

适用范围与读者完成后能获得的结果。

## 前提与背景
## 操作步骤或机制分析
## 验证与失败定位
## 局限、版本与参考来源
```

性能数字必须同时提供硬件、模型、负载、基线与测量口径。无法复核的数字应移除或明确标记为待核查，不能从一种硬件外推到所有设备。

## 选择合适的目录

| 目录 | 内容 |
| --- | --- |
| `tutorials/` | 有明确起点和完成条件的学习与操作路线 |
| `tech-notes/` | 机制分析、问题定位、实验观察 |
| `standards/` | 写作、代码评审、复现与维护约定 |
| `resources/` | 带选择理由和适用场景的资料索引 |
| `achievements/` | 可核实的系统与成果介绍 |

## 提交前核对

先检查材料是否允许公开，尤其是从内部文档提炼的内容。移除密钥、内部地址、个人联系方式清单、未授权数据与未公开实验。链接应优先指向官方文档、原始论文和维护中的公开仓库。

在仓库根目录运行：

```bash
npm ci
npm run typecheck
npm run build
```

构建通过后检查文章页面、侧边栏、站内搜索和深浅色主题下的可读性。文档内部使用相对链接，外部材料使用完整 URL；页面改名时修复所有引用。

将修改提交到 [intellistream/sage-wiki](https://github.com/intellistream/sage-wiki)。有直接维护权限的成员可以按仓库规则提交到主分支，其他贡献者通过 PR 评审。合并后确认 Pages 部署成功，并检查线上正文，而不只看构建状态。

## 过期内容如何处理

时间敏感条目记录最后核查日期；安装命令以对应版本的官方兼容矩阵为准；历史实验保留条件和日期。发现错误时同时检查正文、首页导航、相关页面和分身知识库，避免只修一份副本。

具体同步和删除流程见[知识维护指南](../tutorials/knowledge-maintenance.md)。
