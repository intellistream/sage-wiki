## 目的

本文总结了系统方向论文（尤其是面向 SIGMOD、OSDI、EuroSys、ATC 等系统会议）在多轮修改中反复执行的写作要求与改稿规范。适用于系统论文、综述类文章的终稿打磨。

核心原则：**论文应像一篇严谨的系统论文，而非实验室流水账。** 科学有效性优先，其次结构清晰，最后视觉打磨。任何以提升视觉效果为由损害公平比较、准确语义或叙事纪律的决策都应被拒绝。

---

## 1. 科学有效性规则

### 1.1 不要混合不可比的操作区间

- 零拒绝行和拒绝行不是公平对等的比较对象，不应在同一图中以同等地位呈现。
- 若某策略的延迟降低是以牺牲拒绝率为代价，该代价必须在正文、表格和图中保持显式可见。
- 拒绝点可以作为参考点讨论，但不应在零拒绝比较面板中视觉主导。

### 1.2 有真实数据就用真实数据

- 若正确实验数据存在，从正确结果重绘图，而非保留旧但更美观的图。
- 论文中不应保留与实验结果矛盾但视觉上方便的图。
- 声明、数据点、表格行、图注在每次修改后必须保持一致。

### 1.3 保持服务代价显式可见

- 不要将某机制呈现为无代价的同输出加速。
- 当高优先级请求的救援依赖于整形、延迟或准入选择时，低优先级工作所支付的代价必须保持可见。
- 请求输出预算 vs 有效输出预算是结果的一部分，而非实现脚注。

### 1.4 显式标注证据成熟度与来源

- 若引用包含预印本、已录用但未发表论文、或本组工作，在证据姿态部分以透明脚注标注。
- 区分：(a) 稳定发表的论文，(b) 已录用待最终出版的论文，(c) 未经同行评审的 arXiv 预印本。
- 自引是可接受的——当被引工作暴露了其他地方不可用的控制面时，但集中度应被承认。

### 1.5 明确你的故障模型

- 安全包络和恢复讨论应显式分类所假设的故障模型：crash-stop、crash-recovery with replay、network partition、Byzantine 或 silent degradation。
- 在一种故障模型下成立的不变量可能在另一种下悄悄失效；论文必须说明针对哪一种。

## 2. 结构写作规则

### 2.1 节开头应干净

- 一节开头通常应包含一个简洁的引导段，然后才进入第一个小节。
- 不要在第一个小节之前堆叠多个短设置段落，除非每个段落承担明确不同的工作。

### 2.2 禁止单句占位段落

- 不要留一个单句作为独立段落，当它只是引入表格、图、附录或列表时。
- 典型坏模式：一句"表 X 展示了……"独立成段。
- 如果该句仅是过渡，将其合并到前后段落中。

### 2.3 避免正文中的无序列表（除非列表结构本身重要）

- 正文中，紧凑散文优先于仅枚举字段或属性的短列表。
- 视觉上浪费垂直空间的列表应改写为一句紧凑的散文。
- 列表在结构本身具有分析重要性时可接受；否则不应打断阅读流。

### 2.4 讨论类节优先使用统一的粗体摘要段落

- Discussion 和 Related Work 用少量统一的 `\paragraph{...}` 块组织更好。
- 每块以清晰的粗体摘要声明开头，然后立即在同段落中讨论。
- 避免模糊的标题如"Out of scope."；使用具体的声明性标题。

### 2.5 Introduction 末尾应有论文大纲段

- 添加一个简短的论文大纲段在引言末尾。
- 大纲应按节顺序描述论文。
- 不要从子节标签（如 Section 2.2）开始，从外层节号开始（如 Section 2）。

### 2.6 不要在每个 callout box 中重复同一论点

- quotebox 或 keybox 应推进论证，而非重述中心论点。
- 如果同一核心声明在引言、多个章节和结论中重复出现，读者感知到的是循环性而非渐进深度。
- 每个 callout 应引入新的面向或相对该节证据锐化声明。

### 2.7 拆分密集散文墙为可导航子单元

- 超过约 4 页密集引用散文的小节应拆分为带主题标题的 `\subsubsection{}` 块。
- 标题应命名智识内容，而非仅"Part 1 / Part 2"。

### 2.8 结论收紧到 1–2 个聚焦段落

- 结论不应重述论文；应蒸馏出最关键的一个可操作要点。
- 一段核心教训 + 一段前瞻含义通常对综述或系统论文足够。

### 2.9 显式定位于相邻综述传统

- 写综述时，显式说明你的分析单元与相邻综述传统（如存储引擎综述、缓存管理综述、模型中心 ML 综述）有何不同。
- 每个相邻传统一段差异化说明，防止审稿人问"这和 X 有什么不同？"

## 3. 图表规则

### 3.1 图语义必须与表语义匹配

- 图标签必须与对应表格行名完全一致。
- 图例条目、直接标签或图注短语不应暗示与表格不同的方法名。
- 高亮区域、辅助框和虚线标注不是方法，不应看起来像方法。

### 3.2 保持视觉风格纪律和一致

- 实验点使用黑色描边标记。
- 图例优先放在绘图区外；否则使用不遮挡数据的轻量框图例。
- 使用节制的虚线引导和需要时白底直接标签。
- 当提升可读性时直接标注焦点系统。

### 3.3 表格不应浪费宽度或产生布局伪影

- 若表格没有 `X` 列，`tabularx` 通常不是正确工具。
- 当目标是固定宽度下稳定列填充时，优先使用 `tabular*`。
- 注意奇怪的空白条、超宽或可见不平衡的空白。

### 3.4 合并或移除概念冗余的图

- 若两图传达相同概念点在不同抽象层次，保留分析价值更高的那个。
- 每张图必须证明其页面成本：它说出了文字单独不能说的什么？

### 3.5 比较表应标注证据置信度

- 当表格跨论文比较机制时，添加"Confidence"或"Validation depth"列标注每行声明的验证深度。
- 使用紧凑量表（如 A/B/C 或符号）并在图注中定义。

## 4. 综述特有规则

### 4.1 运行示例必须反复出现，而非仅被引入

- 若定义了运行示例（如"Example A: streaming fraud detector"），在每个适用的小节中以名字回引。
- 每次回调应是具体句子展示该小节机制如何操作于该示例，而非仅"recall Example A"。

### 4.2 形式脚手架必须在表格和综合分析中使用

- 若引入形式化记号（如五元组），在比较表头、跨域综合分析段落和推导示例中显式使用。
- 仅在一个引言段落中出现后再不出现的脚手架是装饰性的，而非分析性的。

### 4.3 使传播声明可通过推导示例证伪

- 当声明"局部决策作为约束传播到其他轴"时，用具体数字追踪至少一个决策穿越所有轴。
- 推导示例应产生可证伪预测。

### 4.4 将愿望蓝图框定为概念参考模型

- 若蓝图今天无法实现，显式说明并列出前提条件。
- 命名什么需要先存在（如便携式状态模式语言、有界延迟遥测契约、策略组合代数）。

### 4.5 自引审计

- 计算自引数量并与总引用比较；若超过 ~8–10%，添加正当性说明。
- 对每个自引，验证它暴露了其他被引工作中不可用的控制面或机制。

---

## 5. 页面预算纪律

- 不含参考文献的正文必须保持在页数限制内。
- 附录移动是可接受的——当它们将支持性但非中心材料从主叙事中移除时。
- 移除冗余 callout box 和合并图是回收页面空间最低风险的方式。

---

## 6. 修改前检查清单

每次保留一项论文修改前，逐项确认：

- [ ] 此改动是否使比较更诚实？
- [ ] 是否有图现在将不可比区间当作严格对等比较？
- [ ] 是否有标签偏离了对应表格行名？
- [ ] 是否引入了一句话占位段落？
- [ ] 是否添加了本应是散文的正文列表？
- [ ] 是否有 callout box 仅重述了之前的而没有添加新面向？
- [ ] 运行示例是否以名字回引（而非仅引入后被遗忘）？
- [ ] 形式化记号是否在表格和综合分析中使用（而非仅在散文定义中）？
- [ ] 预印本和自引是否以适当透明说明标注？
- [ ] 安全/恢复讨论是否命名了假设的故障模型？

若任何一项不满意，改动尚未完成。
