# RAG 系统设计与实践

Retrieval-Augmented Generation (RAG) 将检索系统与 LLM 生成结合，是知识问答的一类常见架构。是否需要 RAG，取决于知识更新频率、可追溯性、延迟与回答质量要求。

## RAG 架构

```
用户查询 → 候选召回（向量/关键词/混合）→ 可选精排 → 证据筛选 → LLM 生成 → 回答与引用
```

核心组件：
1. **Embedding 模型**：将文本转为向量表示
2. **向量索引**：ANNS (Approximate Nearest Neighbor Search) 索引
3. **Reranker（可选）**：对候选文档进行精排；是否启用应比较质量收益与额外时延
4. **生成模型**：基于检索上下文生成回答

## 检索质量优化

### 混合检索

结合向量检索和关键词检索（BM25）的优势：
- 向量检索：语义匹配能力强
- BM25：精确匹配能力强
- 融合策略：Reciprocal Rank Fusion (RRF) 或线性加权

### Query 改写

- **HyDE**：让 LLM 先生成假设性答案，再用答案做检索
- **Query Expansion**：扩展查询词，提高召回率

### 链接结构增强

Wiki 链接可作为候选扩展信号，但不能直接视作相关性证据。可以比较“不扩展 / 1-hop 扩展 / 仅人工策划链接扩展”的 recall、误召回、端到端质量与时延；在有测量结果前，不应宣称链接扩展必然提高召回率或保持低延迟。实验设计参见 [Benchmark 指南](../resources/inference-benchmark-guide.md)。

## 与知识库系统的整合

RAG 系统通常需要一个高质量的知识库作为检索源：
- 结构化 wiki（如 Docusaurus）提供天然的组织结构
- 知识图谱方案（如 GraphRAG）增加了实体关系但成本高
- 轻量级方案利用现有链接结构，成本更低

## 同时评测 RAG 的效果与性能

评测 RAG 不能只看回答是否流畅，也不能只看模型生成速度。**在同一批带版本的测试问题上，分别测检索质量、答案与引用质量、完整请求的延迟和吞吐，再检查质量与时延是否同时满足预先声明的验收条件。** 重排、改写和更多上下文可能改善质量，也会增加调用、排队和计算成本；是否值得需要同负载对照，不能凭是否启用某个组件下结论。

以下是可复用的评测方法，不是本课题组服务已经达到的成绩，也不声明某个模型或优化必然更好。指标概念参考 [Ragas 指标文档](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)、[ARES](https://arxiv.org/abs/2311.09476)、[信息检索评估教材](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)和 [vLLM 在线 benchmark 文档](https://docs.vllm.ai/en/stable/cli/bench/serve/)；下面的实验组织、日志字段及联合准入方式是本文建议的评测协议。

### 1. 固定测试集、知识快照和判分规则

为每道问题保留 `case_id`、问题文本、允许访问的来源范围、语料提交或快照、相关文档/段落 ID、必要事实要点，以及预期可回答性。文档 ID 应带版本；重复 chunk 不能冒充多个独立相关文档。将调参集与最终验收集分开，不能看完验收答案后再调整参考答案或放宽门槛。

测试集应覆盖直接事实、多部分问题、多文档综合、相近但不相关文档、过期/冲突版本、没有足够资料的问题，以及身份权限边界。不能只挑系统已经回答好的问题。参考答案允许多种表达，但必须列清回答应覆盖的事实、证据和允许的不确定性；没有唯一措辞不等于无法评价。

知识库没有足够信息时，应评价是否正确说明缺口、是否避免编造，而不是强迫生成肯定答案。对本来可回答的问题，不完整回答或不必要的拒答仍然是失败，不能靠增加拒答来提高忠实度。

### 2. 分开测检索、答案和引用质量

| 层次 | 建议记录的指标 | 如何判定与注意事项 |
| --- | --- | --- |
| 检索覆盖 | Recall@k、必要事实/证据覆盖率 | 用人工标注的相关集合或必要事实核对前 k 项是否找全；固定 k 和标注单位。有多个必要证据时，“命中一篇”不代表完整覆盖。 |
| 检索排序与噪声 | Precision@k；按任务选 MRR、nDCG | 区分相关材料是否靠前、无关材料是否挤占上下文。MRR 关注首个相关结果，不适合单独衡量多证据完整性；分级相关标注可使用 nDCG。 |
| 答案正确性与完整性 | 参考事实覆盖、错误事实率、任务成功率 | 逐项检查问题各部分，核对当前有效来源；不能只做关键词命中。客观短答案可用规范化后的精确匹配，开放回答需明确量表与人工抽查。 |
| 答案忠实度 | 被检索证据支持的可核验陈述比例 | 检查陈述是否能从实际给模型的证据推出。忠实于错误或过期来源不代表答案正确，也不代表回答了用户的问题。 |
| 引用质量 | 引用支持准确性、需引事实的引用覆盖率、链接有效性 | 核对引用是否支持相邻结论、是否遗漏必要引用，以及来源版本、权限、完整 URL 是否正确；有链接或 HTTP 200 不等于证据相关。 |
| 边界行为 | 可回答问题的错误拒答率；不可回答问题的正确缺口说明率；越权泄漏次数 | 正确拒答与错误拒答分开统计。权限测试必须检查实际取证与输出，不能只看最终措辞是否谨慎。 |

这里的 Precision@k 是前 k 项中相关项的占比，不应与工具里同名或近似名的指标混用。例如，Ragas 的 [Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) 可以按参考答案的事实陈述是否被上下文支持来评价；其 [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 检查回答陈述与检索上下文的一致性。使用时记录库版本、具体指标类、输入字段、裁判模型和规则，不能只写一个“RAG 分数”。

LLM 裁判是估计工具，不是独立真相。保留按难度和失败类型分层的人审样本，检查裁判与人工的分歧；不能只让生成模型给自己打分。对引用和版本还需做确定性核对。修改裁判、提示或参考数据后，必须重新评估可比性；不同裁判产生的分数不能直接拼接。

### 3. 测完整请求，不只测生成引擎

从客户端发起请求到完整、经过校验的最终答案可用，记录端到端耗时。分别保留排队、查询改写、embedding、召回、reranker、证据筛选、模型生成、来源校验和交付时间。并行阶段记录真实起止时间和关键路径，不能把重叠阶段机械相加；引擎侧耗时与用户侧耗时应分开报告。

同时报告 p50/p95/p99 延迟、TTFT、生成阶段的 TPOT/ITL、成功请求吞吐、输出 token 吞吐、超时/拒绝/错误率，以及输入输出 token 和外部调用成本。TTFT 要注明是首个模型 token、首个用户可见答案 token，还是来源校验后首段可发布答案；思考或进度事件不能冒充最终答案。TPOT 也要注明计时边界和输出 token 口径，不能把模型生成结束后仍在进行的校验时间藏掉。

在固定到达率下改变并发，在固定并发下改变负载都可以形成实验，但不能混为同一组对照。记录实际到达率和长度分布，分别测试冷启动、预热后稳态、缓存命中与未命中；报告语料索引构建/更新的耗时和资源占用，但不要把离线构建时间混入每次在线查询。

超时、截断、校验拒绝和交付失败都应计入总请求数。成功请求的延迟分位数必须标明只覆盖成功样本，并另报失败分布与超时阈值；超时观测是耗时下界，不能将其当作正常完成值，或把失败样本丢掉后宣称尾延迟改善。离线 LLM 评分的耗时不属于在线响应时间；若生产流程在线调用核验模型，则其时间必须计入。

### 4. 用配对消融定位质量与时延的取舍

固定生成模型及版本、推理配置、硬件配额、语料快照、问题集合、提示模板、输出预算、到达轨迹和缓存条件。每轮只改变一个因素，例如 BM25/向量/混合召回、候选数量 k、reranker 开关、查询改写或证据选择方式；先运行基线，再用相同样本运行处理组，随机化或交替安排执行顺序。

同时比较每道问题的质量变化和耗时变化，按多部分、不可回答、长上下文等子集报告结果。若增加 k 后 Recall@k 提高但答案变差，应检查噪声与证据选择；若重排改善事实覆盖但延迟超过要求，应如实呈现取舍，不能只报质量或速度的一边。必要时增加人工提供正确证据的诊断组，以区分检索失败与答案组织失败；诊断组不能冒充实际系统成绩。

保留多次独立重放及配对差值，按问题或重放的相关结构估计置信区间；同一请求的重复采样不能冒充独立样本。未显著改善、样本不足和真正的质量退化要区分，不应只挑最好的一轮。具体负载控制参考 [推理系统 Benchmark 指南](../resources/inference-benchmark-guide.md)。

### 5. 以质量约束下的有效吞吐作联合判断

先声明必须覆盖的事实、允许的错误/拒答水平、引用规则、权限约束，以及 TTFT、端到端时延等 SLO，再测量，不应在看到结果后选择有利门槛。严重的越权或错误归因可设为硬失败，但门槛数值必须由任务风险和用户需求确定，本文不提供通用“合格分数”。

vLLM benchmark 的 goodput 可按时延 SLO 筛选请求，但这本身不检查 RAG 事实或引用质量。本文建议另报**质量与 SLO 联合有效吞吐**：在统一观测窗口内，同时通过完整性/质量规则、正常交付和时延约束的请求数，除以窗口时长；另报这些请求占全部请求的比例。质量可离线判定后按请求 ID 关联；没有完成质量标注的请求不能默认为通过。

比较方案时先检查硬约束，再看质量、p95/p99 延迟、联合有效吞吐和成本。一个方案速度更快但漏答、引用错误或拒答更多，不能宣布为无代价优化；若没有方案在所有维度占优，应给出可选取舍，而不是压成一个掩盖失败的总分。

### 6. 最小可复核交付

交付测试集与语料修订号、实验配置、可重放请求轨迹、去敏后的逐请求结果、分层指标表、裁判版本/人工核对记录和失败样例。逐请求记录至少包含 `case_id`、配置 ID、证据 ID 与版本、答案/引用核对结果、阶段耗时、完成状态、token 数及失败原因；公开报告不得包含私有文档、访问令牌或个人会话。

验收顺序是：先核对相关资料是否能召回，再核对答案是否完整且有据，最后在相同质量要求下进行负载实验。单次真实问答可以证明该链路当次工作，不能代替系统级性能或质量评测。这样才能回答“效果是否更好、代价是什么、结论能否复现”，而不只是证明模型能输出一段文字。
